## Objective

Define the smallest safe decision boundary for the first non-synthetic candidate
admitted to `qaos-worker`. Reconcile the verified transport with canonical Artifact,
Objective, Task and QueueItem ownership. Produce DECISION-REQUEST-022 without
transferring or executing candidate bytes.

## Existing contract

- Artifact owns immutable UTF-8 content, opaque identity, SHA-256 digest and bounded
  provenance. The title is display/compatibility data, not transport identity.
- Objective and Task IDs provide request correlation. Neither infrastructure nor a
  provider may replace them with its own job identity.
- QueueItem.result is the existing durable execution-evidence location. A worker
  adapter must not create a second product job or verdict registry.
- The installed broker authenticates and validates framed transport, but the fixed
  launcher currently admits only the reviewed `harmless` fixture. Transport success
  is VERIFIED; real generated-code validation or designation is not established.
- An independently owned acceptance Artifact must determine pass/fail. Candidate
  output cannot approve itself, publish itself, mutate tests or select an entrypoint.

## Recommended first admission

Use one dependency-free, bounded Python pilot candidate represented by one immutable
Artifact and one separately authored immutable acceptance Artifact. It must not
contain QAOS repository source, `.git`, configuration, provider credentials,
OmniRoute state or dependency downloads. A later work order would add one new fixed,
digest-pinned launcher fixture and a provider-neutral controller adapter for this
specific pilot only.

The pilot should prove real generated bytes can be correlated, transferred,
executed without network or credentials, assessed by independent tests, cleaned up
and recorded in the originating QueueItem. It must not prove or claim that the
worker is ready to build QAOS, run OpenHands, accept arbitrary projects, or promote
artifacts automatically.

## Alternatives

- A QAOS patch subset would be closer to the intended ecosystem but immediately
  introduces multi-file source selection, repository-context, test selection and
  patch/publication authority. Defer until the isolated single-candidate contract is
  validated.
- A whole QAOS checkout would exceed the current 8 MiB/32-member contract, expose
  unrelated source/configuration and blur controller/worker authority. Reject as a
  first admission.
- Continuing synthetic fixtures cannot validate generated candidate handling and
  would not advance the stated objective.

## Scope and verification

Architecture/control-plane records only. No product code, tests, credentials,
worker/cloud state, launcher, broker, Artifact data, QueueItem data, OmniRoute or
network configuration changed. No candidate, acceptance bundle or QAOS source was
transferred. Verify JSON parsing and repository whitespace only.

## Stop condition

Stop for the selections in DECISION-REQUEST-022. Even approval will authorize only
a separately scoped local admission-contract implementation first; live candidate
transfer remains a later explicit gate after independent review.
